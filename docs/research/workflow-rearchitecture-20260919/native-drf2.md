## 1. Decision and evidence boundaries

Keep **`PipelineOrchestrator` and `pipeline_state.json` as DRF authority**. Native DeerFlow is a useful execution harness; its gateway owns native chat runs, not DRF stage completion. `drf2` contains an executable scaffold with deterministic gates and reused engine adapters, but its actual producer/consumer contracts are not ready for cutover. An architecture plan should improve explicit boundaries around the current authority and require parity before substituting a new driver.

## 4. Failure and recovery map

**Native lead graph.** The shared chain begins with tool-output budgeting, thread data, optional uploads, sandbox, dangling-tool repair and LLM error handling; optional guardrails precede sandbox audit and tool-error conversion ([H/agents/middlewares/tool_error_handling_middleware.py:129-249](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/agents/middlewares/tool_error_handling_middleware.py:129)). Lead-only composition adds dynamic context, slash skill activation, optional summarization/todos/token tracking, title, memory, vision/deferred-tool filtering, task limit, loop detection, custom middleware, safety termination and final clarification ([H/agents/lead_agent/agent.py:271-380](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/agents/lead_agent/agent.py:271)). Ordering is behavior, particularly reverse `after_model` safety dispatch; preserve it with assembly tests rather than another general middleware rewrite.

LLM middleware retries selected transient errors, refuses quota/auth retries, and uses an instance-local circuit ([H/agents/middlewares/llm_error_handling_middleware.py:108-244,297-398](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/agents/middlewares/llm_error_handling_middleware.py:108)). Failure becomes an `AIMessage` carrying `deerflow_error_fallback`. The gateway worker checks that flag and ends error ([H/runtime/runs/worker.py:358-365](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/runtime/runs/worker.py:358)); the vendor subagent executor lacks that check but the DRF overlay adds it. Ordinary tool exceptions become error `ToolMessage`s, while `GraphBubbleUp` control signals are rethrown ([H/agents/middlewares/tool_error_handling_middleware.py:97-126](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/agents/middlewares/tool_error_handling_middleware.py:97)). This split must not accidentally swallow a fatal provenance/compaction exception in a broad retry/fallback catch.

Clarification appends a tool message and returns `Command(goto=END)` ([H/agents/middlewares/clarification_middleware.py:137-156](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/agents/middlewares/clarification_middleware.py:137)). It is a conversational stop; an ended native graph is not proof that DRF stage deliverables were produced. DRF-2 should require explicit stage outcomes and fresh artifact receipts, including awaiting-user, instead of inferring domain success from `RunStatus.success` alone.

**Native persistence and restart.** [H/runtime/checkpointer/async_provider.py:91-202](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/runtime/checkpointer/async_provider.py:91) preserves legacy standalone checkpointer precedence, then unified database selection, then in-memory fallback. In-memory fallback does not provide process-crash durability. [N/app/gateway/deps.py:145-236](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/app/gateway/deps.py:145) binds stores/infrastructure at startup, reconciles persisted inflight rows only for SQLite, and drains tasks before resource closure. `RunManager` keeps live in-memory control state over hydrated history ([H/runtime/runs/manager.py:402-471](/Users/rogerlin/Downloads/DeepResearchForecast/deer-flow-2.0.0/backend/packages/harness/deerflow/runtime/runs/manager.py:402)). A hydrated record is readable but not locally cancellable or streamable. Admission lock and task handles are process-local; the source does not establish distributed worker leases.

`cancel()` persists interrupted after signaling/cancelling the asyncio task (`manager.py:512-541`). Shutdown is bounded and explicitly logs tasks that outlive drain (`:700-790`). Rollback restores a checkpoint snapshot or empties a thread, preserving pending writes (`worker.py:456-546`); it does not revert files, graph writes, network calls or simulation jobs. Snapshot capture/restore errors can be logged with rollback unfulfilled (`worker.py:199-201,339-382`). Keep this distinction visible to a domain orchestrator.

Journal flush, completion-data persistence and thread metadata updates can fail non-fatally (`worker.py:400-434`). A successful stream ending therefore needs a separate durability/usage-coverage indicator if used as a research-stage acceptance receipt. Existing retry and drain code should be extended rather than replaced by a new global scheduler.
